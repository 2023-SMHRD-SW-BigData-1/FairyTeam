# 당신편 무료 배포 완전정복 (초보용)

> 작성: 2026-06-14 / 상태: **아직 미실행 — 계획서**
> 비전공 초보 기준, "왜 이걸 하는지"까지 적은 버전. 순서만 보려면 배포_기록.md.

## 들어가기 전에 — "배포"가 뭐야? 왜 해?
내 컴퓨터에서만 돌던 당신편은 나만 볼 수 있고, 컴퓨터 끄면 끝.
"배포"는 24시간 켜진 남의 컴퓨터(서버)에 올려서, 인터넷 주소만 있으면
누구나 들어올 수 있게 하는 작업. = 가게를 길거리에 여는 것.

## 1. 왜 서비스가 3개나 필요해? (Vercel + Render + DB)
당신편은 성격이 다른 3덩어리로 나뉜다:
- **화면(프론트)**: 손님 눈에 보이는 메뉴판. 자주 안 바뀌고 빠르게 뿌리기만 하면 됨.
- **백엔드(API+소켓)**: 주문 받고 DB 다루고 **실시간 채팅 중계**하는 주방. 항상 돌아야 함.
- **데이터(DB)**: 회원·상품·거래·채팅이 쌓이는 창고. 사라지면 안 됨.
성격이 다르니 각각 제일 잘하는 무료 서비스에 따로 맡긴다:
- 화면 → **Vercel** (정적 화면 뿌리기 끝판왕)
- 백엔드 → **Render** (서버 24시간 + **WebSocket 지원** ← 채팅 때문에 중요)
- DB → **TiDB Cloud / Railway** (데이터 보관)
- 원본 코드 → **GitHub** (위 3곳이 여기서 코드를 가져감)

> ❗당신편 포인트: 채팅이 Socket.io(WebSocket) 라서, WebSocket 막는 호스팅이면 채팅이 안 된다.
> Render는 WebSocket을 지원하므로 OK. (정적 호스팅만 되는 곳에 백엔드 올리면 안 됨)

## 2. 전체 그림
```
GitHub(fairy 코드)
   ├─ fairy-next/         → Vercel  (화면)
   └─ fairy-next/server/  → Render  (백엔드+소켓) ── 연결 ──> DB(TiDB/Railway)
손님 → Vercel 화면 → (주소 호출) → Render 백엔드 → (주소 호출) → DB
                         └──── WebSocket(채팅) ────┘
```
포인트: 화면·백엔드·DB가 "서로의 인터넷 주소"를 알아야 연결된다. 그게 마지막 STEP 4.

## 3. 우리는 모노레포 — Root Directory가 핵심
한 저장소 안에 프론트(fairy-next)와 백엔드(fairy-next/server)가 같이 있다.
그래서 배포할 때 **"어느 폴더를 볼지"(Root Directory)를 꼭 지정**해야 한다.
- Vercel Root Directory = `fairy-next`
- Render Root Directory = `fairy-next/server`
이걸 안 하면 "빌드할 게 없다"거나 엉뚱한 폴더를 빌드해서 실패한다.

---

## STEP 1. DB 먼저 (창고부터)
**무엇:** 클라우드에 빈 MySQL을 만들고 우리 테이블을 심는다.
**왜:** 백엔드가 붙을 창고가 있어야 하니까.
**순서:**
1. TiDB Cloud 가입 → **Starter(무료)** 생성 (유료 Dedicated 누르지 말 것)
2. 접속정보(Host/User/Password) 확인
3. `schema.sql` → `seed_categories.sql` → `seed.sql` 순서로 실행
   (카테고리가 상품보다 먼저 들어가야 외래키 안 깨짐 — run-sql.js가 이 순서대로 함)
4. TiDB는 보안연결(SSL) 필요 → 나중에 백엔드 환경변수에 `DB_SSL=true`

## STEP 2. 백엔드 (주방)
**무엇:** server 폴더를 Render가 돌려서 API+소켓 서버를 띄운다.
**왜:** 화면이 데이터를 받아오고 채팅하려면 주방이 떠 있어야 하니까.
**순서:**
1. Render → New → Web Service → 저장소 연결
2. **Root Directory = `fairy-next/server`**, Start Command = `node server.js`, Free
3. 환경변수: DB 접속정보 + `DB_SSL=true` + `JWT_SECRET`(길게) + `CORS_ORIGIN`(나중에 프론트 주소)
4. 주소 나오면 `/api/health` 열어 `"FAIRY API 살아있어요"` 확인
**무료 한계:** 15분 미접속 시 잠들어 첫 요청이 느림(10~50초). 데모용은 괜찮음.

## STEP 3. 프론트 (매장)
**무엇:** fairy-next를 Vercel이 빌드해 화면을 띄운다.
**순서:**
1. Vercel → Import → **Root Directory = `fairy-next`** (Vite 자동인식)
2. 환경변수 `VITE_API_BASE` = STEP2의 Render 주소
3. `vercel.json` 에 SPA rewrites (새로고침 404 방지)
4. Deploy → 주소 확인
**이때 데이터가 안 나오면:** 보통 VITE_API_BASE 오타거나 다음 STEP을 안 해서.

## STEP 4. 서로 소개시키기 (제일 자주 빠뜨림)
- 백엔드 `CORS_ORIGIN` ← **프론트(Vercel) 주소** 넣고 재배포
  (안 하면 "CORS 차단"으로 API·채팅 다 막힘)
- 프론트 `VITE_API_BASE` ← **백엔드(Render) 주소**
  (채팅 소켓도 이 주소로 붙음 — lib/socket.js 가 API_BASE 사용)
- 둘 다 맞으면: 상품·찜·위탁거래·실시간 채팅까지 인터넷에서 동작.

## 자주 나는 문제 (체크리스트)
- [ ] 화면은 뜨는데 데이터 X → VITE_API_BASE / 백엔드 잠듦 / CORS_ORIGIN
- [ ] 채팅이 연결 안 됨 → 소켓 주소(VITE_API_BASE) 확인, 호스팅 WebSocket 허용 여부
- [ ] 다시 로그인하라고 함 → JWT_SECRET 이 로컬과 다르면 옛 토큰 무효(정상)
- [ ] 카테고리 비어있음 → seed_categories.sql 을 schema 다음·seed 전에 실행했는지
- [ ] 이미지 사라짐 → Render 무료 디스크는 재배포 시 초기화. 운영은 외부 저장소(Cloudinary 등)

## 비용 요약
- 전부 무료 티어로 데모 가능. 단 Render는 잠들고, 무료 DB는 용량·기간 제한 있음.
- 실제 상업 운영 시: 백엔드 유료 인스턴스(안 잠듦) + 관리형 DB + 이미지 스토리지 + 실결제 PG.
